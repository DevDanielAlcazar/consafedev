# ConSafeDev — Experience Contract

## Strategic idea

**Engineered Clarity**

ConSafeDev visually and narratively transforms:

fragmentation → understanding → architecture → software → operation → clarity.

The website must demonstrate ConSafeDev's engineering quality before claiming it.

## Desired user reaction

The target reaction after Hero + Living System is:

> “Si así piensan y construyen su propia experiencia, quiero saber qué pueden construir para mi operación.”

The site must feel:
- premium;
- precise;
- contemporary;
- technically credible;
- highly intentional;
- alive without being chaotic;
- expressive without resembling an AI-generated agency template.

## The ConSafeDev Effect

Build 01 is accepted only if all six are true:

1. The Hero makes it clear that ConSafeDev solves real business problems with custom software.
2. The first scroll creates curiosity to continue.
3. Motion improves understanding rather than decorating content.
4. Fragmentation → clarity remains understandable even if explanatory copy is ignored.
5. The result cannot be mistaken for a generic AI/SaaS landing.
6. After Living System, the user should infer that ConSafeDev understands product design and software engineering.

## Two visual environments

### Engineering Space
Purpose:
- complexity;
- systems;
- architecture;
- activity;
- transformation.

Character:
- deep;
- precise;
- controlled;
- dark, but never “dark AI neon”.

### Clarity Space
Purpose:
- understanding;
- trust;
- explanation;
- decision.

Character:
- bright;
- editorial;
- spacious;
- calm.

Build 01 ends at the transition toward Clarity Space.

## Hero

Approved prototype copy:

### Headline
**Lo complejo puede funcionar simple.**

### Supporting copy
**Diseñamos software a medida que conecta procesos, automatiza operaciones y convierte problemas reales de negocio en sistemas que funcionan.**

### Primary CTA
**Hablemos de lo que necesitas resolver**

### Exploration cue
**Explora cómo lo hacemos**

Hero visual concept:
- a fragmented but controlled operational system;
- 12–18 meaningful entities on desktop;
- incomplete relationships;
- limited teal;
- no fictional KPIs;
- no stock-office image;
- no generic dashboard floating in space.

## Living System narrative

The Hero system becomes the Living System. It must feel like one continuous physical scene, not two unrelated sections.

Story states:

### 1. Fragmentation
**Los problemas rara vez empiezan en el software.**

Optional supporting sentence:
**Empiezan entre procesos, herramientas y decisiones que dejaron de trabajar juntas.**

### 2. Understanding
**Primero entendemos qué está ocurriendo.**

Optional supporting sentence:
**Porque construir bien empieza mucho antes de escribir código.**

### 3. Architecture
**Diseñamos alrededor del problema. No de una plantilla.**

### 4. Software
**Después lo convertimos en software que tu equipo puede usar.**

### 5. Living system
**Un sistema que trabaja como trabaja tu negocio. No al revés.**

## System entities

Use a restrained set such as:
- Clientes
- Operación
- Ventas
- Documentos
- Datos
- Soporte
- ERP
- Personas
- Inventario
- Mensajería
- Reportes
- Procesos

Possible friction labels:
- manual
- duplicado
- pendiente
- sin conexión
- revisión

Use sparingly.

## Forbidden visual language

Do not use:
- purple neon / cyberpunk aesthetics;
- aurora gradients as the principal background;
- glowing blobs;
- random particles;
- AI brains;
- robot imagery;
- 3D globes;
- abstract floating cubes;
- fake code terminals;
- fake dashboards used only as decoration;
- generic Bento grids;
- huge glassmorphism capsules;
- excessive pills;
- tech-logo marquees as a primary visual;
- stock teams staring at laptops;
- exaggerated performance numbers;
- made-up efficiency metrics.

## Page transition principle

Future routes `/agenda` and `/privacidad` must behave as chapters of the same product.

Rule:
**Changing route must never feel like changing product.**

Build 01 should establish the reusable Persistent Site Shell required for this later behavior.
